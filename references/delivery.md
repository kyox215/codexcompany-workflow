# 产品交付十阶段

用于新 App、新产品或影响范围较大的业务路径。开始时先按项目规则接续。可把多阶段写进现有一份方案，沿用现有编号、组件和发布机制。

| 阶段 | 做什么 | 通过条件 |
| --- | --- | --- |
| 1. 目标与现状 | 写明用户、场景、期望结果、平台、现有行为、权限和项目归属。记录本轮范围与不在本轮的目标。 | 用户结果明确，关键未知有负责人或取证办法。 |
| 2. 验证问题 | 收集最少的真实反馈、可观察现象或公开依据，标明时间、环境和样本。写出关键假设、指标定义及测量办法。 | 有支持证据，或明确以首版为验证实验。 |
| 3. 首版范围与规格 | 选择一条从入口到结果的完整路径。按必要、以后、排除划范围。给重要行为分配 REQ，写条件→动作→预期结果。 | 成功判据、失败提示和恢复路径均可观察。 |
| 4. 状态、权限与数据 | 核字段、默认值、校验、稳定 ID、数据拥有者、真实读写位置与权限。定义取消、重复、超时、失败、重开和旧数据的行为。 | 写入确认、读回和不确定结果核对方式清楚，重试与并发保持一致。 |
| 5. 交互与视觉 | 按任务顺序定义入口、主操作、返回、取消和完成落点。覆盖适用的空、加载、失败、无权限、大字、键盘与暗色状态，沿用已定品牌与组件。 | 关键行为清楚，必要时看实际预览。关键视觉取舍提供可比较候选。 |
| 6. 工程切片 | 核实际工具链、依赖、接口与现行实现，高风险能力按授权先做可行性检查。每片从入口到用户结果，包含数据和验证，声明依赖与文件所有权。 | 每片可由下一执行者独立理解并验证。 |
| 7. 实现 | 从正常入口接通界面、业务规则、保存和读回。实现失败恢复后再打磨。标注模拟响应或尚未接通的环节。 | 第一条用户路径已完整走通，受影响旧行为有检查。 |
| 8. 验证和验收 | 绑定候选，逐项核成功、关键失败、重复、取消、返回、重开和相关回归。复杂任务由独立 QA 按[协作规则](operations.md)复测。 | REQ 有通过、失败或未验结果，能定位证据。 |
| 9. 发布准备与交付 | 核源码、构建与包或部署的对应关系，检查适用的隐私、支持、权限、商店信息和回退条件。 | 有可审阅候选。实际发布后另存回执和访问或安装验证。 |
| 10. 反馈与迭代 | 对照原目标记录实际反馈，区分缺陷、体验和新需求。带上样本、版本、环境和优先级。 | 形成下一条最小可交付路径，明确需重新验证的证据。 |

## 裁剪与往返

- 已有功能优先记录现状与变更差异。遇到状态、权限、导航或业务语义变化时补相应检查。
- Bug 先取得能够区分原因的复现证据。验证修复前失败、修复后通过，按风险覆盖相邻路径。低影响文字、样式改动在实际产物中查看即可。
- 设计可因工程可行性回到受影响页面。规格纠正时更新同一 REQ 的状态、切片与验收。候选改变后重新跑受影响场景，并说明复用证据对应的版本。
- 含 AI 能力时写明输入输出、允许动作、质量判据和错误处理。分开生成建议、用户确认、正式写入。用已获准的样本覆盖缺信息、冲突、无效输出及超时。
- 只交设计或内容时说明呈现和验证范围。截图用于布局观察，交互过程用操作记录或录像，业务保存由读回或重开验证。真实设备、账号、外部服务和发布需要各自证据。

复制[规格卡、切片卡与发布卡](templates.md)时可合并字段，保持同一 REQ 与准确候选。
